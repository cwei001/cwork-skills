# 工作协同系统概述

**版本**: v1.0 | **更新时间**: 2026-03-04

---

## 一、系统目标

《工作协同》是一套企业内部的任务与汇报协同系统，核心目标是：
- 让任务被清晰拆解
- 让汇报被有效判断
- 让决策可以被记录和追踪

---

## 二、核心对象

### 2.1 任务 (Task)

| 属性 | 说明 |
|------|------|
| **创建人** | 任务发起者 |
| **指派人** | 任务执行者 |
| **标题** | 任务名称 |
| **目标** | 任务要达成的目的 |
| **要求** | 具体执行要求 |
| **截止时间** |  deadline |
| **优先级** | high / medium / low |
| **状态** | 进行中 / 已结束 |

**重要**：任务没有"直接完成"按钮，必须通过提交汇报来完成。

---

### 2.2 汇报 (Work Report)

| 属性 | 说明 |
|------|------|
| **创建人** | 汇报提交者 |
| **接收人** | 汇报接收者 |
| **标题** | 汇报主题 |
| **内容** | 汇报正文（支持HTML） |
| **类型** | 1（普通汇报） |
| **关联任务** | 可关联任务ID |
| **需要决策** | 是否需要领导决策 |

**特点**：
- 可多次提交（一个任务可以有多条汇报）
- 可被反馈
- 可形成决策/建议

---

### 2.3 反馈 (Feedback)

| 属性 | 说明 |
|------|------|
| **汇报ID** | 关联的汇报 |
| **内容** | 反馈意见 |
| **类型** | comment（评论）/ escalate_to_task（升级为任务） |

**特点**：
- 可文字回复
- 可升级为新任务
- 任务完成后可回填原反馈

---

### 2.4 决策/建议 (Decision)

| 属性 | 说明 |
|------|------|
| **汇报ID** | 关联的汇报 |
| **类型** | decision（决策）/ suggestion（建议） |
| **内容** | 决策意见 |

**注意**：只有汇报的接收人可以填写决策/建议

## 四、场景判断逻辑

### 4.1 快速判断表

| 用户表述 | 意图 | 后续操作 |
|---------|------|---------|
| "创建任务""指派任务" | 任务管理 | 调用 /task/create |
| "查询任务""我的任务" | 任务管理 | 调用 /task/list |
| "查看任务详情" | 任务管理 | 调用 /task/detail/{taskId} |
| "提交汇报""发汇报" | 汇报管理 | 调用 /work-report/report/record/submit |
| "我发出的汇报""发件箱" | 汇报管理 | 调用 /work-report/report/record/outbox |
| "收到的汇报""收件箱" | 汇报管理 | 调用 /work-report/report/record/inbox |
| "回复汇报" | 汇报管理 | 先查 inbox 获取 ID，再调用 reply |
| "反馈""评论" | 反馈管理 | 调用 /feedback/create |
| "反馈升级为任务" | 反馈管理 | 调用 /feedback/escalate |
| "查看反馈" | 反馈管理 | 调用 /feedback/list/{reportId} |
| "决策""同意/不同意" | 决策 | 先查 inbox/pending 获取 ID，再调用 decision/submit |
| "待决策" | 决策 | 调用 /decision/pending |
| "完成任务" | 任务管理 | 先提交汇报，再调用 task/complete |

### 4.2 特殊场景处理

#### 场景 A：回复某汇报
- 需要先通过 inbox 查询获取汇报 ID
- 如果标题不明确，需告知用户查询结果让其确认

#### 场景 B：给某汇报决策
- 需要先通过 inbox 或 pending 查询获取汇报 ID
- 确认是"决策(decision)"还是"建议(suggestion)"

#### 场景 C：通过汇报完成任务
- 需要两步：
  1. 提交汇报（获取 reportId）
  2. 调用任务结束接口（传入 taskId + reportId）
